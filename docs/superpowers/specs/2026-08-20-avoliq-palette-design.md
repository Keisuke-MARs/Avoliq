# Avoliq — Spotlight風タスク管理パレット 設計書

作成日: 2026-08-20
ステータス: ユーザー承認済み（ブレインストーミングセッションにて各セクション承認）

## コンセプト

世界一使いやすく、簡単でシンプルだがスマートでめっちゃかっこいいタスク管理アプリ。
macOSのどこからでもグローバルホットキーで呼び出し、**キーボード操作だけ**でタスクの
CRUD・ステータス更新が完結する。UI/UXに特化する。

## 決定事項サマリ

| 項目 | 決定 |
|---|---|
| アプリ形態 | Spotlight風フローティングパレット（NSPanel） |
| ボード表示 | パレット内にステータスごとの縦レーン（カンバン） |
| 詳細表示 | ドリルイン型（同一パレット内で盤面⇄詳細を切替） |
| ボード | 複数ボード対応・切替可能 |
| ステータス | ボードごとに自由に追加/削除/改名/色/並び順。新規ボードはデフォルト4つ（未着手/進行中/確認中/完了） |
| データ保存 | ローカルSQLite（同期なし） |
| 本文 | Markdownテキスト（BlockNoteでNotion風編集） |
| ホットキー | デフォルト ⌥Space（ユーザーがSpotlight側を別キーへ移す）。設定で変更可能 |
| アイコン | 絵文字は使わず lucide-react |
| フォント | -apple-system（SF Pro） |
| 技術 | Tauri v2 + React + TypeScript + shadcn/ui + Tailwind + BlockNote + rusqlite |
| スコープ外 | MCPサーバー連携（ただしデータモデルは対応可能に設計）、iCloud等の同期、モバイル |

## アーキテクチャ

```
┌─ macOS ──────────────────────────────────────┐
│  ⌥Space (グローバルホットキー)                  │
│    └→ Tauri v2 シェル (Rust)                  │
│        ├ NSPanel化したフローティングウィンドウ    │
│        │   └ React + TypeScript (WebView)     │
│        │      ├ shadcn/ui + Tailwind + lucide │
│        │      └ BlockNote (Notion風エディタ)   │
│        ├ メニューバー常駐アイコン(開く/終了)      │
│        └ SQLite (rusqlite・Rust側で一元管理)   │
└──────────────────────────────────────────────┘
```

- **Tauri v2（Rust）** が土台。ウィンドウは `tauri-nspanel` でNSPanel化し、他アプリから
  フォーカスを奪わずに最前面へ浮かぶSpotlight風の挙動を実現する。⌥Spaceで表示/非表示
  トグル、Escで非表示。
- **UIはReact + shadcn/ui + lucide-react**。フォントは `-apple-system`（SF Pro）。
  Markdown編集は **BlockNote**（Tiptapベース・Notion風ブロックエディタ、
  `# ` `- ` `[] ` ` ``` ` のライブ変換標準装備）を採用。エディタは自作しない。
- **DBアクセスはRust側リポジトリ層に一元化**。フロントエンドはTauriコマンド経由で
  読み書きするのみ。将来のMCPサーバーが同じリポジトリ層・同じSQLiteファイルを
  再利用できる構造にする。
- DBファイルは `~/Library/Application Support/Avoliq/` に配置。
- ログイン時自動起動（tauri-plugin-autostart、設定でOFF可）。
- メニューバー常駐アイコン（開く / 設定 / 終了）。Dockアイコンは出さない。

## データモデル（SQLite / MCP対応を見据える）

```sql
boards    id(UUID) / name / position / created_at / updated_at
statuses  id(UUID) / board_id → boards / name / color / position
          / created_at / updated_at
tasks     id(UUID) / board_id → boards / status_id → statuses
          / title / content_md / position / created_at / updated_at
          / deleted_at(NULL=生存)
schema_migrations  version / applied_at
```

- ステータスはボードごとのレコード。新規ボード作成時にデフォルト4つ
  （未着手 / 進行中 / 確認中 / 完了）を自動投入。
- 本文は `content_md` に素のMarkdownテキストで保存する。DBの中身が人間にもAIにも
  そのまま読める形式であることが将来のMCP連携の要。
- 削除は `deleted_at` によるソフトデリート（undo・復元の土台）。
- 全IDはUUID（将来の同期・外部連携で衝突しない）。
- スキーマは `schema_migrations` でバージョン管理し、MCP追加時の拡張に備える。

## キーボード操作仕様

### グローバル
| キー | 動作 |
|---|---|
| ⌥Space | パレット表示/非表示トグル（どこからでも） |
| Esc | 詳細→ボードに戻る / ボード→パレットを閉じる |

### ボード画面（カンバン）
| キー | 動作 |
|---|---|
| 文字入力 | 検索バーへ即入力→リアルタイム絞り込み |
| Enter（入力あり・カード未選択） | その名前で新規タスク作成→詳細で本文入力へ |
| ↓ | 検索バーからボードへフォーカス移動 |
| ←→↑↓ | カード間移動（レーン跨ぎ含む） |
| Enter（カード選択中） | 詳細を開く（ドリルイン） |
| ⌘←→ | 選択カードのステータスを隣レーンへ移動 |
| ⌘↑↓ | 同レーン内の並び順変更 |
| ⌘⌫ | タスク削除（ソフトデリート）。⌘Zで復元 |
| ⌘N | 新規タスク（検索バーへフォーカス） |
| ⌘1〜9 | ボード直接切替 |
| ⌘B | ボードスイッチャー |
| ⌘, | ボード設定（ステータスの追加/削除/改名/色/並び順。全操作キーボード可） |

### 詳細画面
| キー | 動作 |
|---|---|
| 入力 | BlockNoteでNotion風編集・即時自動保存 |
| ⌘←→ | 詳細を開いたままステータス変更 |
| ⌘T | タイトル編集へフォーカス |
| Esc | ボードへ戻る（保存操作は不要） |

新規作成のゴールデンパス:
「⌥Space → タスク名を打つ → Enter → 本文を書く → Esc → Esc」で
マウスに一度も触れず完結する。

## エラー処理

- **二重起動防止**: tauri-plugin-single-instance で常に1プロセス。
- **ホットキー衝突**: ⌥Spaceの登録に失敗した場合（Spotlightが未変更のままの場合等）、
  起動時に通知を出し、設定画面から別キーへ変更できるようにする。
- **DB書き込み失敗**: パレット内に控えめなトースト表示。編集内容はフロント側に保持し、
  リトライ可能にする。
- **自動保存**: 本文はデバウンス（500ms）で保存。パレット非表示時に強制フラッシュし、
  Escで即閉じても内容を失わない。

## テスト方針

- **Rust（リポジトリ層）**: cargoユニットテスト。CRUD・ステータス移動・並び順・
  ソフトデリートをインメモリSQLiteで検証。
- **React**: Vitest + Testing Library。キーボード操作→状態変化のテストを厚く書く
  （移動 / 作成 / ステータス変更 / undo）。
- 実装はTDD（superpowersワークフロー）で進める。
- E2E（実ウィンドウ・実ホットキー）は自動化コストが高いため、手動スモーク
  チェックリストで代替する。

## 実装体制

- メインセッション（Fable 5）は設計・監査・レビューに専念し、実装はOpus/Sonnetの
  サブエージェントへ切り出す。実装難易度が特に高い箇所のみメインセッションが担当。
- UI実装はUIUX専門のスキル/エージェントを調査し、それを使ったエージェントに依頼する。

## 却下した代替案

- **Electron**: 常駐アプリとしてはメモリ消費が重く、軽快さのコンセプトに合わない。
- **SwiftUIネイティブ**: 見た目は最もApple純正に近いが、Notion風ブロックエディタの
  自作コストが非常に高く、shadcn/lucideも使えない。
- **横展開型詳細（盤面+詳細の2ペイン）**: パレットが巨大化し「サッと出してサッと消す」
  体験が損なわれるため、ドリルイン型を採用。
- **Markdownファイル群での保存**: 並び順・メタ情報の管理が複雑化するためSQLiteを採用。
  本文をMarkdownテキストのまま列に持つことで両者の利点を取る。
